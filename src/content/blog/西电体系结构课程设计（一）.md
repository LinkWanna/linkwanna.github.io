## 术语解读

### 微指令

我们课设的 CPU 是 CISC 架构，需要设计一套微指令集，微指令的本质就是对 CPU 内部操作的细粒度控制，微指令中的每一个字段都可以在 CPU 的设计中找到对应的管脚定义。

多个微指令可以组合成复杂的操作，比如 x86 指令集中的 `MOV` 指令，可能需要多个微指令来完成数据的读取、写入和寄存器的更新，主要还是因为同一时刻总线上只能有一个输出信号。（采用哈佛架构的 CPU 就有效避免了这种使用微指令的尴尬局面）

落到我们的课设上，我们需要读懂微指令中的每一个字段定义，然后根据这些字段的含义来设计微指令的实现，也就是修改 ROM 中的数据。

### 总线

总线（Bus）是 CPU 内部各个组件之间传输数据的通道，是实实在在物理的线。在课设的 CPU 设计中，所有的数据传输都通过总线进行，包括寄存器之间的数据传输、ALU 的输入输出等。在 CPU 的设计中，总线通常是多路复用（Multiplexing）的，这意味着在同一时刻只能有一个组件向总线输出数据，而其他组件则从总线读取数据，千万千万不要让两个或两个以上的组件同时向总线输出数据，轻则就会发生总线冲突（Bus Contention），导致数据错误，重则会烧毁硬件（左零右火，雷公助我！！！）。

这也是为什么我们的电路中会使用唯一的 B 字段来控制总线的输出信号，确保在任何时刻只有一个组件能够向总线发送数据。

## 寄存器声明

在课设的 CPU 设计中，提供了一个 8 个寄存器：
- **PC**: 程序计数器（Program Counter），指向下一条指令的地址（执行 RAM 中）
- **AR**：地址寄存器（Address Register），存放当前指令的地址
- **IR**：指令寄存器（Instruction Register），存放当前指令的内容
- **R0, R1, R2**：通用寄存器（General Purpose Registers），用于存放临时数据
- **DR1, DR2**：数据寄存器（Data Registers），用于在总线和 ALU 之间缓冲数据 

在文档中，还可以看到很多对寄存器的操作信号，文档中并没有对其进行标识：
1. **LDxxx**：加载信号，将数据从总线加载到指定寄存器中（bus -> reg），例如 `LDDR1`，将数据从总线加载到寄存器 R1 中。
2. **xxx-B**：输出信号，将指定寄存器的数据输出到总线（reg -> bus），例如 `RD-B`，将目标寄存器（具体是哪一个通用寄存器取决于操作码 (opcode) 中的 `rd` 字段）的数据输出到总线。

## 微指令文档解读

这部分是出了名的模糊，文档压根就没有说清楚每一个字段的语义，这对于我们理解微指令的设计是非常不友好的。

![](/assets/images/blog/architecture-design-1/micro_inst.webp)

我这里尝试重新整理了一遍。

1. **uA[5\:0]**: 下一条要执行的微指令的微地址。
    - 这个字段的值决定了微指令的执行顺序。
    - 微地址指向 ROM 中的某个位置，那里存放下一条需要执行的微指令。

2. **C 字段**：
 
| C[2] | C[1] | C[0] | 含义|
|---|---|---|-----------|
| 0 | 0 | 0 | 无操作   |
| 0 | 0 | 1 | P(1)   |
| 0 | 1 | 0 | P(2)：无效操作   |
| 0 | 1 | 1 | P(3)：无效操作   |
| 1 | 0 | 0 | P(4)   |
| 1 | 0 | 1 | AR：无效操作     |
| 1 | 1 | 0 | LDPC：PC 的时钟信号 |

从电路图上看，`C` 字段的实现十分地令人困惑，P(1) ~ P(4) 是用于做条件控制的，具体的条件控制逻辑在 `uI_C` 模块中进行实现。`AR` 没有任何作用，AR 管脚没有连接到任何地方。我们CPU上 PC 是一个8位的计数器，每个时钟上升沿都会自增 1，`LDPC` 控制 PC 的时钟信号，使得 PC 在 `T4` 时钟周期上升沿时更新其值。 

3. **B 字段**：B 字段决定了哪一个信号会输出到总线上

| B[2] | B[1] | B[0] | 含义  |
|---|---|---|-----------|
| 0 | 0 | 0 | 无操作         |
| 0 | 0 | 1 | RS-B： RS -> Bus      |
| 0 | 1 | 0 | RD-B： RD -> Bus      |
| 0 | 1 | 1 | RJ-B： RJ -> Bus      |
| 1 | 0 | 0 | SFT-B：SFT -> Bus     |
| 1 | 0 | 1 | ALU-B：ALU -> Bus     |
| 1 | 1 | 0 | PC-B： PC -> Bus      |

`B` 字段同样有不少匪夷所思的问题，`RJ-B` 唯一的作用就是使得 `R2` 寄存器的信号无法输出到总线上，它的信号和 `ALU_MD:LDR0_2` 中的 `R2_B` 信号相与，导致了 `R2` 寄存器永远无法输出到总线上。`SFT-B` 也是一个无用的信号，电路图中并没有任何地方连接到 `SFT-B` 信号。


> 你可以发现有一些操作在文档上其实是留空的呢，因为这是我根据 cpu 设计中的各个字段自己扣出来的呀！天哪，老师居然让我们在文档上做填空题！！！


4. **A 字段**：A 字段决定了哪个寄存器会接收总线上的数据

| A[2] | A[1] | A[0] | 含义  |
|---|---|---|-----------|
| 0 | 0 | 0 | 无操作         |
| 0 | 0 | 1 | LDRI： Bus -> RD      |
| 0 | 1 | 0 | LDDR1：Bus -> DR1      |
| 0 | 1 | 1 | LDDR2：Bus -> DR2      |
| 1 | 0 | 0 | LDIR： Bus -> IR      |
| 1 | 0 | 1 | LOAD： Bus -> PC      |
| 1 | 1 | 0 | LDAR： Bus -> AR      |


5. **A9 A8**：这两个字段决定 RAM、DOUT、SW（实验箱按钮）哪一个的信号会输出到总线上

| A9 | A8 | 含义  |
|---|---|-----------|
| 0 | 0 | SW   -> Bus      |
| 0 | 1 | RAM  -> Bus      |
| 1 | 0 | DOUT -> Bus      |
| 1 | 1 | 无操作         |

6. **WE**：控制 RAM 的写使能信号

7. **S 字段 + M 字段 + Cn 字段**：这三个字段共同决定了 ALU 的操作类型，具体参考下面的 Python 代码

一个一个地看完这些微指令的字段，终于可以开始做实验了。但是我的眼睛不是尺，24 位的微指令，光看着就头大，更别说还要手动地去翻译成对应的操作了。正因如此，我写了一个 Python 脚本来帮我翻译微指令。现在值需要输入 16 进制的微指令，我就可以看到会发生什么样的操作了。


```python
ALU_map = {
    ("0000", "0"): "A + CN",
    ("0000", "1"): "~A",
    ("0001", "0"): "(A | B) + CN",
    ("0001", "1"): "~(A | B)",
    ("0010", "0"): "(A | ~B) + CN",
    ("0010", "1"): "(~A) & B",
    ("0011", "0"): "0 - CN",
    ("0011", "1"): "0",
    ("0100", "0"): "A + (A & ~B) + CN",
    ("0100", "1"): "~(A & B)",
    ("0101", "0"): "(A | B) + (A & ~B) + CN",
    ("0101", "1"): "~B",
    ("0110", "0"): "A - B - CN",
    ("0110", "1"): "A ^ B",
    ("0111", "0"): "(A & ~B) - CN",
    ("0111", "1"): "A & ~B",
    ("1000", "0"): "A + (A & B) + CN",
    ("1000", "1"): "(~A) | B",
    ("1001", "0"): "A + B + CN",
    ("1001", "1"): "~(A ^ B)",
    ("1010", "0"): "(A | ~B) + (A & B) + CN",
    ("1010", "1"): "B",
    ("1011", "0"): "(A & B) - CN",
    ("1011", "1"): "A & B",
    ("1100", "0"): "A + A + CN",
    ("1100", "1"): "1",
    ("1101", "0"): "(A | B) + A + CN",
    ("1101", "1"): "A | ~B",
    ("1110", "0"): "(A | ~B) + A + CN",
    ("1110", "1"): "A | B",
    ("1111", "0"): "A - CN",
    ("1111", "1"): "A",
}

A9_8_map = {
    "00": "DEV -> Bus",
    "01": "RAM -> Bus",
    "10": "Bus -> DOUT",
    "11": "无操作",
}

A_map = {
    "000": "无操作",
    "001": "Bus -> RD  ",
    "010": "Bus -> DR1 ",
    "011": "Bus -> DR2 ",
    "100": "Bus -> IR  ",
    "101": "Bus -> PC",
    "110": "Bus -> AR  ",
}

B_map = {
    "000": "无操作         ",
    "001": "RS -> Bus      ",
    "010": "RD -> Bus      ",
    "011": "RJ -> Bus      ",
    "100": "SFT -> Bus     ",
    "101": "ALU -> Bus     ",
    "110": "PC -> Bus      ",
}

C_map = {
    "000": "无操作   ",
    "001": "P(1)     ",
    "010": "P(2)：无效操作 ",
    "011": "P(3)：无效操作 ",
    "100": "P(4)     ",
    "101": "无操作    ",
    "110": "PC += 1 / BUS -> PC",
}

WE_map = {
    "0": "无操作",
    "1": "BUS -> MEM",
}


class Inst:
    def __init__(self, S, M, Cn, WE, A9_8, A, B, C, uA):
        self.S = S
        self.M = M
        self.Cn = Cn
        self.WE = WE
        self.A9_8 = A9_8
        self.A = A
        self.B = B
        self.C = C
        self.uA = uA

    def from_binary(value: str):
        S = value[0:4]
        M = value[4:5]
        Cn = value[5:6]
        WE = value[6:7]
        A9_8 = value[7:9]
        A = value[9:12]
        B = value[12:15]
        C = value[15:18]
        uA = value[18:24]

        return Inst(S, M, Cn, WE, A9_8, A, B, C, uA)

    def from_hex(value: str):
        binary_value = bin(int(value, 16))[2:].zfill(24)
        return Inst.from_binary(str(binary_value))

    def to_binary(self):
        return f"{self.S}{self.M}{self.Cn}{self.WE}{self.A9_8}{self.A}{self.B}{self.C}{self.uA}"

    def to_hex(self):
        return hex(int(self.to_binary(), 2))

    def __str__(self):
        uA_hex = hex(int(self.uA, 2))
        return (
            f"hex: 0x{self.to_hex()[2:].zfill(6).upper()}\n"
            f"bin: 0b{self.to_binary().zfill(24)}\n"
            f"S: {self.S}       \t\t=> {ALU_map[(self.S, self.M)]}\n"
            f"M: {self.M} \n"
            f"Cn: {self.Cn}\n"
            f"WE: {self.WE}     \t\t=> {WE_map[self.WE]}\n"
            f"A9_8: {self.A9_8} \t\t=> {A9_8_map[self.A9_8]}\n"
            f"A: {self.A}       \t\t=> {A_map[self.A]}\n"
            f"B: {self.B}       \t\t=> {B_map[self.B]}\n"
            f"C: {self.C}       \t\t=> {C_map[self.C]}\n"
            f"uA: {self.uA}   \t\t=> {uA_hex.zfill(2)}\n"
        )


if __name__ == "__main__":
    print(Inst.from_hex("0x010220"))
    print(Inst.from_hex("0x01E21D"))
```

## 答疑环节

Q: 为什么我的 `LOAD` 无效？
A: `LOAD` 信号接入了 `REGS_MD:counter` 模块的 `LOAD` 管脚，这是一个同步置位信号，只有在时钟上升沿时才会更新 PC 的值。也就是说，你需要在 `T4` 时钟周期的上升沿时，`LOAD` 信号为高电平，PC 才会更新其值。结果就是，想要 `LOAD` 生效，还必须同时激活 C字段中的 `LDPC` 信号。
Q: A 字段里 LDRI 中的 `RI` 指的是什么？
A: RI 来自与 opcode 中的 `rd` 字段：**00：无操作**，**01：R0**，**10：R1**，**11：R2**。
