## 时钟：step3


![](/assets/images/blog/architecture-design-2/step3.png)

在课设的 CPU 设计中，时钟信号是通过 `step3` 模块提供的，它本质上是一个 `step 信号控制的 5 拍单次移位节拍发生器`，名字还有点长，下面简单解析一下：

1. **step 信号控制**： `step` 信号连接到我们实验箱的 `M7` 按键，当按下这个按键时，`step` 信号会被拉低，触发一个微指令周期。
2. **5 拍**：每次按下 `step` 按键，`step3` 模块会依次产生 5 个时钟周期（`T1`，`T2`，`T3`，`T4`，`T5`），每个周期对应一个微指令的执行阶段。`T5` 会比较特别，它是用来锁住 `step3` 模块的状态，直到下一次按下 `step` 按键。
3. **单次移位节拍发生器**：`step3` 模块的核心是一个 5 位的移位寄存器（`shift register`），每次按下 `step` 按键，移位寄存器会从初始状态 `00001` 开始，依次移位产生 5 个时钟周期的信号。


### 答疑环节

第一次遇到这个模块的时候可能就会疑惑了：

Q：按下一次 `step` 按键，会发生什么？

A：CPU 会完整地执行一条微指令，经历 4 个时钟周期。（第五个时钟周期用来锁住状态）

Q：那如果我想要执行多条微指令呢？

A：那就多按几次 `step` 按键呗，每按一次，就会执行一条微指令。多按几次，就会执行多条微指令。

Q：`T5` 是怎么锁住状态的？

A：在 `T5` 为高电平后，`T5` 和 `clk` 会通过一个或门，使得 **移位寄存器组**的时钟输入被一直拉高，没有时钟上升沿，移位寄存器组就不会再移位了。

### 时序分析

有了时钟之后，我们就可以分析微指令的时序了，我们可以观察图中 `T1~4` 信号分别去了什么地方，由此来判断每个小节拍中 CPU 内部发生了什么。

1. **T1**：访存周期
    - `RAM8`：访问内存，用来读取指令和操作数。
    - `uP_ROM`：读取当前的微指令。
2. **T2**：寄存器读写周期
    - `REGS_MD`：内部包含 `IR`，`AR`，`PC` 三个寄存器和 `DOUT` 这个来自外部的输入寄存器，`T2` 期间，会将总线上的值加载到这四个寄存器中，是否被加载取决于微指令。
    - `ALU_MD`：内部包含 `R0`，`R1`，`R2` 三个通用寄存器和 `DR1`，`DR2` 两个数据寄存器，`T2` 期间，会将总线上的值加载到这五个寄存器中，是否被加载取决于微指令中的 `LDxxx` 字段。
    - `uI_C`：在 `T3` 部分
3. **T3**：微指令地址更新周期
    - `uI_C`：微指令控制器，`T2` 和 `T3` 期间启动，它的输出 `SE[6:1]` 会在此时从 `'6b11_1111` 变成一个有效值，与下一条微指令信号 `M[6:1]` 一起控制 `uA_reg` 的更新状态。
    - `uA_reg`：地址寄存器，`T3` 上升沿会根据微指令的要求更新其值。
4. **T4**：PC 更新周期
    - `REG_MD:PC`：仅连接到 `PC` 寄存器，需要激活 `LDPC` 信号才能实现更新。
5. **T5**：状态锁定，等待下一次 `step` 按键的按下。

总结一下，`step3` 模块的作用就是将每次按下 `step` 按键，转换成 5 个时钟周期的信号，这样我们就可以通过按键来控制 CPU 的微指令执行。在每个时钟周期中，CPU 内部的各个组件会根据微指令的要求进行相应的操作，从而实现指令的执行！


## REGS_MD：寄存器模块

![](/assets/images/blog/architecture-design-2/REGS_MD.png)

这个模块包含了 CPU 内部的部分寄存器，包括：
- `IR`：指令寄存器，存储当前执行的指令。
- `AR`：地址寄存器，存储当前访问的内存地址。
- `PC`：程序计数器，存储下一条要执行的指令地址。
- `DOUT`：外部数据输入寄存器，存储从外部输入的数据。

这个模块没有太多需要关心的地方，唯一需要注意的是总线的连接方式：**只有 PC 和 RAM 的数据会输出到总线上。**

## ALU_MD：算术逻辑单元模块

![](/assets/images/blog/architecture-design-2/ALU_MD.png)

这个模块包含了 CPU 内部的部分寄存器和算术逻辑单元（ALU），包括：
- `LDR0_2`：R0~R2 的加载控制单元。具体的输出和输出的映射关系，可以参考上一章中微指令解析的部分。
- `R0`，`R1`，`R2`：三个通用寄存器，用于存储操作数和结果。
- `DR1`，`DR2`：两个数据寄存器，用于临时存储数据。作为 ALU 的输入缓冲区，会在 ALU 执行操作时提供数据。
- `ALU`：算术逻辑单元，执行加法、减法等操作。

`ALU` 的实现使用的是上个学期的 `ALU181A`，可以去查上学期的文档，不过那真的很难看呀，所以在这里我提供了一个表格：
```c
//  Operation Table (S, M):
//      S       | M=0 (Arithmetic)                  | M=1 (Logic)
//      --------|-----------------------------------|--------------------------
//      0000    | A + CN                            | ~A
//      0001    | (A | B) + CN                      | ~(A | B)
//      0010    | (A | ~B) + CN                     | (~A) & B
//      0011    | 0 - CN                            | 0
//      0100    | A + (A & ~B) + CN                 | ~(A & B)
//      0101    | (A | B) + (A & ~B) + CN           | ~B
//      0110    | A - B - CN                        | A ^ B
//      0111    | (A & ~B) - CN                     | A & ~B
//      1000    | A + (A & B) + CN                  | (~A) | B
//      1001    | A + B + CN                        | ~(A ^ B)
//      1010    | (A | ~B) + (A & B) + CN           | B
//      1011    | (A & B) - CN                      | A & B
//      1100    | A + A + CN                        | 1
//      1101    | (A | B) + A + CN                  | A | ~B
//      1110    | (A | ~B) + A + CN                 | A | B
//      1111    | A - CN                            | A
```


最后还需要关心总线的问题：**只有 R0~R2 和 ALU 会输出到总线上。**，**只有 R0~R2 会接受总线的输入。**

## uPC：微指令模块


![](/assets/images/blog/architecture-design-2/uPC.png)

本次实验最反人类的模块，没有之一。接下来需要分作**编码器**、**微指令控制**两个部分进行来讲解。

### 编码器

![](/assets/images/blog/architecture-design-2/decoder.png)

这个模块是纯粹的组合逻辑电路，输入是微指令字段 `A`、`B`、`C`、`A8 A9`，分别输入到 `decoder_A`、`decoder_B`、`decoder_C`、`decoder_D` 中进行解码，具体的解码关系可以参考上一章中微指令解析的部分。


> **吐槽：**
为什么 `A8 A9` 不叫 `D` 字段呀，搞得好难受~

由于是组合逻辑电路，所以没有时钟信号，输出会随着输入的变化而变化，也就是说，他们的输出有效时间是 `T1` 时 **uP_ROM** 的微指令输出有效时间，贯穿整个微指令周期。

### 微指令控制

![](/assets/images/blog/architecture-design-2/uI_C.png)


这个部分的设计非常迷惑，非常窒息，源模块几乎没有留下任何的语义信息。


### 模块输入输出

先从简单的 `uA_reg` 开始，它是一个 6 位的寄存器，存储当前微指令的地址。

它的输入 `D[6:1]` 来自于 `uP_ROM` 的输出 `M[6:1]`，决定了下一条微指令的地址。但是这个寄存器不仅受 `D[6:1]` 的控制，还受 `SE[6:1]` 的控制。`SE[6:1]` 来自于 `uI_C` 的输出 `SE[6:1]`，用于强制改变寄存器状态。

这里需要提到 D 触发器的 `PRN` 异步置位引脚：
- 当 `PRN` 为 0 时，D 触发器会被强制置位为 1。
- 当 `PRN` 为 1 时，D 触发器会根据时钟信号的上升沿来更新状态。

也就是说，`uI_C` 是通过 `PRN` 来强制改变 `uA_reg` 的状态的。这是课设 CPU 能够够实现条件跳转的基础（这样的设计真的非常扯~）。

再来看看 `uI_C`，它的输入非常复杂，在这里我逐一解释：
1. `SWA SWB`：这两个信号来自于实验箱上的 `M3` 和 `M4` 按键，一般来说，请直接置为 `2'b11`，即运行程序的模式。
2. `P[4:1]`：这四位信号来自于 `decoder_C` 的输出，决定了条件跳转的条件，具体参考上一章中微指令解析的部分。他们也是可以编程的，我们的文档只使用了 `P[1]` 和 `P[4]`，之后我们可以尝试使用另外两个信号。
3. `I[7:2]`：这六位信号来自于 `IR` 寄存器，由两个部分组成：
   - `I[7:4]`：来自于 `IR` 寄存器的高四位，表示指令的操作码（opcode）。
   - `I[3:2]`：来自于 `IR` 寄存器的中间两位，表示指令的源寄存器（source register）。
4. `FC FZ`：这两个信号来自于 `ALU` 的输出，表示上一次 ALU 操作的结果状态：
   - `FC`：进位标志（Carry Flag），当 ALU 操作产生进位时，该标志被置位为 1。
   - `FZ`：零标志（Zero Flag），当 ALU 操作的结果为零时，该标志被置位为 1。

这个模块是纯粹使用逻辑门来搭建的，估计是直接用卡诺图化简来的，这样的话是没有任何语义信息的，完全就靠我们自己去理解。

### uI_C 逻辑分析

我用 AI 来化简并分析了这个模块的逻辑，得到如下的 `verilog` 代码：

```verilog
module uI_C (
	input  wire        FC,
	input  wire        FZ,
	input  wire        CLK,
	input  wire        SWA,
	input  wire        SWB,
	input  wire [7:2]  I,
	input  wire [4:1]  P,
	output wire [6:1]  SE
);

	wire p1_n = ~P[1];
	wire p2_n = ~P[2];
	wire p3_n = ~P[3];
	wire p4_n = ~P[4];
	wire i7_n = ~I[7];

	assign SE[6] = 1'b1;

	assign SE[5] = ~( (FZ | FC) & CLK & p3_n );
	assign SE[4] = ~( i7_n & CLK & p1_n );
	assign SE[3] = ~( I[6] & CLK & p1_n );
	assign SE[2] = ~( (I[5] & CLK & p1_n) | (I[3] & CLK & p2_n) | (p4_n & CLK & SWB) );
	assign SE[1] = ~( (I[4] & CLK & p1_n) | (I[2] & CLK & p2_n) | (p4_n & CLK & SWA) );
endmodule
```

这个还是比较复杂的，依旧属于人类不可读的范畴，那么我们继续进行基于文档来化简吧：
1. 不考虑 `P[2]` 和 `P[3]`，因为文档中没有使用这两个信号。
2. 不考虑 `FC` 和 `FZ` 信号，因为文档中也没有使用这两个信号。

```verilog
module uI_C (
	input  wire        CLK,
	input  wire        SWA,
	input  wire        SWB,

	input  wire [7:2]  I,
	input  wire [4:1]  P,
	output wire [6:1]  SE
);

	wire p1_n = ~P[1];
	wire p4_n = ~P[4];

    // 固定为 1，即不会影响下一个模块
	assign SE[6] = 1'b1;
	assign SE[5] = 1'b1;

    // P[1] = 0 时，SE[3] = ~I[6], SE[4] = I[7]
    // 其余情况 SE[4:3] = b'11
	assign SE[4] = ~(~I[7] & CLK & p1_n );
	assign SE[3] = ~( I[6] & CLK & p1_n );

    // P[4] = 0 时，SE[2] = ~SWB, SE[1] = ~SWA
    // P[1] = 0 时，SE[2:1] = ~I[5:4]
    // 其余情况 SE[2:1] = b'11
	assign SE[2] = ~( (I[5] & CLK & p1_n) | (p4_n & CLK & SWB) );
	assign SE[1] = ~( (I[4] & CLK & p1_n) | (p4_n & CLK & SWA) );
endmodule
```

### 逻辑验证

现在这个模块就比较好理解了，我们参考文档进行验证：
1. 当使用**控制台微程序**时，`P[4] = 0`，此时 `SE[2] = ~SWB`, `SE[1] = ~SWA` => `uA[2] = SWB`, `uA[1] = SWA`。可以看到，SWA 和 SWB 控制了微指令的低两位，微指令的低两位的变化也刚好对应了微程序流程图的右侧部分。
2. 当使用**运行微程序**时，`P[1] = 0`，此时 `SE[4] = I[7]`, `SE[3:1] = ~I[6:4]` => `uA[4] = ~I[7]`，`uA[3:1] = I[6:4]`。所以可以依照这个规律得到：
    - `IN` ；opcode: 0x00；微指令地址: 8 （八进制：0o10）
    - `ADD`：opcode: 0x10；微指令地址: 9 （八进制：0o11）
    - `STA`：opcode: 0x20；微指令地址: 10（八进制：0o12）
    - `OUT`：opcode: 0x30；微指令地址: 11（八进制：0o13）
    - `JMP`：opcode: 0x40；微指令地址: 12（八进制：0o14）


全部通过了，说明这个模块的逻辑分析是正确的。尽管已经分析明白了，但是我还是觉得这个设计非常反人类，最好最好自己重新设计一个正经的~
